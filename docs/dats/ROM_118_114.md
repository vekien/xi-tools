# ROM/118/114.DAT - Boot-Loaded Numeric Tables (`menu`)

**Path:** `ROM/118/114.DAT`
**Size:** 403,344 bytes
**Magic:** `menu`, version `01 01`
**Loaded:** at boot/start-menu (65 reads in the latest ProcMon trace)
**xiclient label:** `MENU_Unk1` in `LanguageDependentDats`, English file_id `0x51` / 81

This file is a boot-loaded `menu` container, but current evidence says it is **not** the boot/title
screen 2D layout file. It contains fixed numeric tables used by FFXiMain for model/action-style
lookups: `mnc2`, `mon_`, `levc`, `mgc_`, and `comm`.

xiclient independently identifies the English language-dependent slot as `MENU_Unk1`. Through
FTABLE/VTABLE, file_id 81 resolves to `ROM/118/114.DAT`. The name is useful as a client-side label,
but it does not clarify the schema beyond confirming this is a global menu/resource DAT initialized
early.

## Blocks

FFXiMain locates these blocks and stores pointers at `block_start + 0x30` (see the evidence table
below). **On disk the record payload starts at `block_start + 0x10`** — right after the 16-byte
section header — which is what makes the record counts below fit their block ranges exactly
(`mgc_`: `0x41770 − 0x28770 = 0x19000 = 1024 × 0x64`; `comm`: `0x62780 − 0x41780 = 0x21000 =
2816 × 0x30`). Both `mgc_` and `comm` records are **obfuscated per record** (see
[`comm` records](#comm-records-abilities) below); once decoded, the `u16` at rec `+0` is a
sequential id running 0…2815 that equals the record index for every `comm` row.

| Block | Range | Payload | Current interpretation |
|---|---:|---:|---|
| `mnc2` | `0x000020-0x028140` | `0x000030` | Indexed model/animation-style tables |
| `mon_` | `0x028140-0x028550` | `0x028150` | `uint16` lookup table |
| `levc` | `0x028550-0x028760` | `0x028560` | `uint16` level/curve table |
| `mgc_` | `0x028760-0x041770` | `0x028770` | 1024 records of `0x64` bytes, each rotated independently — magic records; see [`mgc_` records](#mgc_-records-spells) |
| `comm` | `0x041770-0x062780` | `0x041780` | **2816** records of `0x30` bytes, each rotated independently — command (ability) records; the client reads `0xB00` of them in some places and `0x700` in others, see [FFXiMain evidence](#ffximain-evidence) |
| `end\0` | `0x062780-0x062790` | `0x062780` | Terminator |

Section header (16 bytes): the 4-char tag, then a `u32` = `(length_in_16_byte_units << 7) |
resource_type` where the length includes the header (`mgc_`: `0x000C80C9` → type `0x49`, `0x1901`
units = `0x19010` bytes; `comm`: `0x001080D3` → type `0x53`, `0x21010` bytes), then 8 zero bytes.
FFXiMain looks the sections up by resource type (`0x49`, `0x53`), so a section may be any length —
`xi dats` grows them to add records past the retail counts ([../menu/records.md](../menu/records.md)).

## FFXiMain evidence

In `pol_decompressed.bin`, the block loader is at VA `0x101670e0` and searches the loaded menu DAT
for these sections. Relevant stores:

| Global | Source block | Notes |
|---|---|---|
| `0x105782a0` | `mnc2 + 0x30` | Only one real consumer found so far, around `0x10101290` |
| `0x1057829c` | `mon_ + 0x30` | Used as a `uint16` lookup table around `0x10142949` |
| `0x10634f58` | `levc + 0x30` | Used as a word table around `0x1022b750` |
| `0x10634f54` | `mgc_ + 0x30` | Iterated as `0x400` records of `0x64` bytes |
| `0x1063462c` | `comm + 0x30` | Iterated as `0x700` records of `0x30` bytes — a **loop bound**, not the on-disk count (the block holds 2816); other consumers read `0xB00` records, see below |

The `mnc2` consumer reads bitfields and indexes tables at offsets such as `+0x80`, `+0x88`, and
`+0x3080`. It does not look like a normal window/frame position parser. The `mgc_`/`comm` consumers
use fixed record strides and action/category fields, not screen-space `x/y/w/h` records.

Every bound on the two tables is listed in CatsEyeXI's cexislots plugin (`cexidats` repo,
`src/cexislots/sites.h`, generated from the decompressed FFXiMain listing: 109 sites, which the
plugin rewrites at load to raise both ceilings to `0x1000`). `mgc_` is `0x400` throughout: the boot
decode loop (`0x19000` bytes = `0x400 × 0x64`), the find-by-name loops, the known-spell list and
the recast array. `comm` uses two numbers, so both lines above hold:

| Records | Where (site names in `sites.h`) |
|---|---|
| `0xB00` (2816) | boot decode loop, `0x21000` bytes (`cmd.decode_loop_end`); known-command list init and refresh (`cmd.ctor_count`, `cmd.refresh_count`); recast lookups (`cmd.recast_bound`) |
| `0x700` (1792) | `/ja` and pet-command id bounds (`cmd.parser_ja_bound`, `cmd.parser_pet_bound`); ids from here up take the mount check (`cmd.band_filter_a/b`); a list reset threshold (`cmd.reset_threshold_imm`) |

So an unpatched client keeps all 2816 rows, but `/ja` resolves only ids below 1792 and treats
1792–2815 as mounts.

## `mgc_` records (spells)

Decoded `mgc_` (spell) record — verified against a retail client and the server's `spell_list`
(`xi.menu.xi_menu_table.SPELL_FIELDS`); the rotation is the one described under
[`comm` records](#comm-records-abilities), with 100-byte records:

| Offset | Type | Field |
|---|---|---|
| `+0x00` | u16 | id — equals the record index for all 1,024 rows |
| `+0x02` | u16 | kind: 1 white, 2 black, 3 summon, 4 ninjutsu, 5 song, 6 blue, 7 geomancy, 8 trust |
| `+0x04` | u16 | element (0 fire … 7 dark, 15 none) |
| `+0x06` | u16 | target bits |
| `+0x08` | u16 | skill (33 healing, 36 elemental, 39 ninjutsu, 43 blue …) |
| `+0x0A` | u16 | MP cost |
| `+0x0C` | u8 | cast time in ¼ s; `+0x0D` u8 recast in ¼ s |
| `+0x0E` | 24 × u16 | level per job in job order (NONE, WAR … RUN, +1); `0xFFFF` = cannot learn |
| `+0x3E` | u16 | menu index — the slot the known-spell list is sorted into |
| `+0x40` | u16 | icon; `+0x42` u16 icon 2; `+0x44…` flags, `+0x62` always `0xFF00` |

## `comm` records (abilities)

The `comm` chunk (section type `0x53`) holds one 48-byte record per ability id. Every record is
scrambled **on its own**: bytes `+0x02`, `+0x0B` and `+0x0C` are stored plain and the population
counts of those three pick a rotate amount, `[1, 7, 2, 6, 3][ |pop(b2) + pop(bC) − pop(bB)| % 5 ]`;
every other byte is rotated left by that amount to decode (right to encode). `mgc_` uses the
identical scheme with 100-byte records. The decoder is `xi.common.xi_menu_records` (ported from
Shining Fantasia's `mgc-decode.ts`), and `mnc2-pos --records` applies it by default.

Decoded layout (what FFXiMain reads):

| Offset | Type | Field |
|---|---|---|
| `+0x00` | u16 | id — equals the record index for all 2,816 rows |
| `+0x02` | u8 | type: 1 ability, 2 pet ability, **3 weapon skill**, 4 job trait, 6 BP: Rage, 8 Corsair's Roll, 9 Quick Draw, 10 BP: Ward, 11 Samba, 12 Waltz, 13 Step, 14 Flourish, 15 Stratagem, 16 Jig, 17 Flourish II, 18 Ready, 19 Flourish III, 20 Monstrosity, 21 Rune Enchantment, 22 Ward, 23 Effusion |
| `+0x03` | i8 | icon id (`+0x04` i16 icon 2) |
| `+0x06` | i16 | charges required |
| `+0x0A` | u16 | target bits (self, pet, party, alliance, PC, mob, NPC…) |
| `+0x0C` | i16 | TP cost |
| `+0x0F` | i8 | level; `+0x10` range, `+0x11` radius, `+0x12` AoE type |
| `+0x13` | u16 | valid-target kind; `+0x15` i8 TP modifier, then TP modifier values |

Counts on this install: 2,816 non-empty records; 512 of type 3. Record 255 (type 3) is
Dimensional Death by the name table; record 259 is type 3 with the placeholder name `.`.
**No offset of the decoded record carries the weapon-skill animation number** — every position
was checked as u8 / u16 / u32 against the 211 known animations (best hit 2/211). Names come from
the matching `d_msg` table `ROM/181/72.DAT` (block *i* ↔ record *i*). The animation banks, the
name table and this table are three separate id spaces; see
[../anim/weapon-skills.md](../anim/weapon-skills.md).

## Tooling

Inspect the known block boundaries:

```bash
uv run xi ui layout mnc2-pos "ROM\118\114.DAT" --block all --limit 20
```

List fixed records from the better-understood blocks (decoded; each `comm` row is named from
`ROM/181/72.DAT`; add `--raw` for the on-disk bytes):

```bash
uv run xi ui layout mnc2-pos "ROM\118\114.DAT" --block comm --records --limit 300
uv run xi ui layout mnc2-pos "ROM\118\114.DAT" --block mgc_ --records --limit 20
uv run xi ui layout mnc2-pos "ROM\118\114.DAT" --block comm --records --raw --limit 20
```

The older `x/y/w/h` candidate scan is still available, but it is only a heuristic and produces many
false positives because the file is dense numeric table data.

## Boot Menu Relevance

This DAT was a strong lead because it is heavily read during boot/start-menu. After static analysis,
it is more likely a general gameplay/model/action table that the client initializes early. It should
not be treated as the primary boot/title 2D position source unless a new runtime test contradicts
the FFXiMain xrefs.
