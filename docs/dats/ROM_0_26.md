# ROM/0/26.DAT — Character Selection Control Variant B (`sel_`)

**Path:** `ROM/0/26.DAT`  
**Size:** 4,448 bytes (0x1160)  
**Magic:** `sel_`  

This is the largest of the small `sel_` files adjacent to the title/login flow. It follows the
same general structure as `ROM/0/24.DAT` and `ROM/0/25.DAT`, but introduces a new `s4xx` record
family and more complex per-record payloads.

Current best interpretation: this file is another title/login or character-selection scene
controller, likely representing a more advanced or more detailed state than `24.DAT` and `25.DAT`.

## Common record shape

Like the other `sel_` files, most `s###` records use the same keyframe layout:

```
+0   char[4]   tag          e.g. "s101"
+4   uint32    type         varies; observed 0x00000486, 0x00000606, 0x00000786, 0x00000A86, 0x00000D86
+8   24 bytes  zeros        reserved / padding
+32  uint32    key_count    number of 0x30-byte keyframes
+36  uint32    flag         sometimes 0, sometimes 1
+40  ...       keyframes    key_count * 0x30 bytes
```

The first three floats in each keyframe are position-like `(x, y, z)` values. Example: `s103` starts
at `0x04A0`; its six keyframe position triples begin at `0x04D0`, `0x0500`, `0x0530`, `0x0560`,
`0x0590`, and `0x05C0`.

Compared with `24.DAT` and `25.DAT`, this file uses a wider range of type/count combinations and
contains longer payloads for some nodes.

Notable constants observed in the payloads include:

| Value | Meaning |
|---|---|
| `0x438B9284` (`279.144f` approx.) | repeated in several `s10x`/`s30x` records |
| `0x438C5B5F` (`280.714f` approx.) | repeated in several records |
| `0x43878282` (`271.020f` approx.) | repeated in `s4xx` records |
| `0x3F800000` (`1.0f`) | common terminator / flag |
| `0x3F2AAAAA` (`0.666...f`) | appears in some multi-state records |
| `0x3F555555` (`0.833...f`) | appears in some multi-state records |

These suggest richer per-node state interpolation than the smaller `sel_` files.

## New `s4xx` family

`26.DAT` is the first of the three files to introduce a full `s4xx` family:

- `s401`
- `s402`
- `s403`
- `s404`

This is its most distinctive feature.

The `s4xx` nodes appear in the embedded `mov1` sequence and are therefore active participants in
the scene/state graph, not dead data.

This makes `26.DAT` a strong candidate for a more complex title/login state, potentially one with
more anchor points, transitions, or interactive parts than `24.DAT` or `25.DAT`.

---

## Larger payload records

Some records in this file are visibly more complex than those in `24.DAT` and `25.DAT`:

- `s103` uses type `0x00000A86` and count `6`
- `s403` uses type `0x00000D86` and count `8`
- `s104`, `s105`, and `s107` use type `0x00000786` and count `4`
- `s106` and `s101` use type `0x00000606` and count `3`

This suggests the file mixes simple anchor nodes with more elaborate multi-key or multi-state
descriptors.

## Control section

The control chain resembles the earlier `sel_` files, but with a larger embedded node list.

### `loop`

`loop` begins at `0x0D10` and references `mov1` in the same general way as the earlier files.

### `mov2`

`mov2` begins at `0x0DA0` and is compact, similar to the smaller helper control blocks seen in
`24.DAT` and `25.DAT`.

### `mov1`

`mov1` begins at `0x0E10` and contains an explicit ordered list of scene/object tags:

Notably, this `mov1` list does **not** include `s201`, `s304`, or `s305`, even though those records
exist elsewhere in the file. That may imply optional states, alternate branches, or non-primary
anchors.

### `main`

`main` begins at `0x10B0` and matches the same dispatch-table pattern seen in the other files:

```
0x10D0  40 00 00 00
0x10D4  50 00 00 00
0x10D8  90 00 00 00
0x10DC  01 00 00 00
...
0x1120  73 05 00 00  00 00 00 00  "loop"
```

So `main` again appears to launch or manage the looped scene sequence rather than store transform
data directly.

## Relationship to `24.DAT` and `25.DAT`

The three `sel_` files now look like related but distinct scene/state controllers:

| DAT | Distinctive traits |
|---|---|
| `ROM/0/24.DAT` | compact; includes `s304`/`s305`; fewer overall nodes |
| `ROM/0/25.DAT` | larger; adds `s106`-`s108` and `s205`-`s206` |
| `ROM/0/26.DAT` | largest; introduces `s401`-`s404` and more complex node payloads |

This strongly suggests the three files correspond to different title/login or character-selection
states rather than redundant copies.

---

## What this file is not

Direct evidence argues against these interpretations:

- Not a texture DAT: no texture names, TXD headers, or image payloads.
- Not the `menu` format from `ROM/0/1.DAT`: no `menu    ` sections or packed 2D menu elements.
- Not an external movie-file reference table: no `.pmv`, `.bgw`, `mov999`, or `music999` strings.

---

## Current hypothesis

`26.DAT` is the strongest candidate so far for a more advanced scene/control state in the
title/login pipeline.

Possible interpretations include:

- a richer character-select or character-creation placement state
- a higher-complexity title/login presentation phase
- a controller that adds the `s4xx` layer for extra anchors, transitions, or UI-linked objects

This remains a hypothesis until record fields can be decoded more precisely and correlated with
visible screen states.
