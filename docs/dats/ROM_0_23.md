# ROM/0/23.DAT — Title Screen Scene (`titl`)

**Path:** `ROM/0/23.DAT`  
**Size:** 73,872 bytes (0x12090)  
**Magic:** `titl`  

This is the FFXI **title screen 3D scene animation file**. It is not a texture or model — it
drives the animated camera and atmospheric rendering that runs in the background while the
login/title screen is displayed. The title screen renders real in-game zones as live 3D
backgrounds; this file contains the zone references, camera spline data, weather state
sequences, and fog/atmosphere parameters that animate the scene.

---

## File header (32 bytes)

```
+0   char[4]  magic      "titl"
+4   uint8    ver_major  0x01
+5   uint8    ver_minor  0x01
+6   uint16   reserved   0x0000
+8   uint32   reserved   0x00000000
+12  uint32   reserved   0x00000000
+16  uint32   reserved   0x20000000  (byte-order marker or unrelated constant)
+20  12 bytes padding    (zeros)
```

The first scene graph node begins at `+0x20` (tag `8c01`).

---

## Scene graph nodes

The body of the file is a flat list of named 4-byte-tagged records. Each tag is an ASCII
identifier; the payload begins at `+4`.  Almost every node starts with the constant
`0x00000486` at `+4`, which appears to be a shared type/version field.

### Node naming conventions

| Prefix pattern | Meaning |
|---|---|
| `8c01`–`9c16` | Early scene graph nodes (camera rig / scene hierarchy) |
| `cg??` | **Control group** — camera spline keyframe sets.  `cga0–cgad`, `cgh0–cghf`, `cgn0–cgnb`, `cgu0–cguc`, `cqa0–cqfb`, `crz0–crzb`, `cpa0–cpaf` |
| `ct10`–`ct2b` | **Control tracks** — 27 named timing/animation channels |
| `mov1`–`mov8` | Camera movement descriptors |
| `1c01`–`7c14` | Mid-section scene graph nodes |
| `c101`–`c403` | Scene binding nodes (camera → zone assignments?) |
| `ex1a`–`ex3e` | Transition or extra-scene nodes |
| `s101`, `s102`, … | Camera sequence nodes (scene-graph labels only — **not** zone identifiers) |

### Control track node layout

Each `ct##` node (e.g. `ct20` at `0x00d760`) is a compact animation channel descriptor:

```
+0   char[4]  name        e.g. "ct20"
+4   uint32   type        0x00000486 (shared constant)
+8   24 bytes zeros       reserved / padding
+32  uint32   keyframe_count  (observed: 2)
+36  28 bytes reserved
+64  float[N×3] position_data  XYZ triplets (world-space camera positions)
```

Example `ct20` keyframes (decoded as float32 LE):
```
  453.27  9.06  15.19   ← keyframe 0 position
  366.72  7.16  10.13   ← keyframe 1 position
```

### Camera group node layout (`cga##`, `cgh##`, etc.)

These nodes hold spline control points. Each has the same header shape as control tracks,
followed by packed float data (XYZ triplets, likely bezier handles).

## Zone sections

The file contains **22 zone sections**, each defining a zone to display plus the
weather/atmosphere/camera state for that zone.  They are located in the range
`0x00deec`–`0x011e00`.

### Zone section structure

Every zone section is introduced by an 8-byte signature immediately before the zone ID:

```
-8   uint64   0x00000000_00067b   section marker
+0   uint32   zone_id             xim zone ID (LE) — see formula below
+4   12 bytes zeros               reserved
+16  ...      weather/fog blocks  variable-length atmosphere sequence for this zone
```

The zone ID uses the same formula as `ZoneTables.kt`:

```
zoneId < 0x100  →  fileTableIndex = 0x64 + zoneId
zoneId ≥ 0x100  →  fileTableIndex = 0x147B3 + (zoneId - 0x100)
```

### Changing a zone

To swap out a zone, patch the **LE uint32 at the zone ID offset** (+0 in the section):

```python
import struct

with open("ROM/0/23.DAT", "r+b") as f:
    f.seek(0x00fdac)          # offset of zone section 12 (North Gustaberg)
    f.write(struct.pack("<I", NEW_ZONE_ID))
```

Compute `NEW_ZONE_ID` from the target zone's file table index:
```
zoneId = fileTableIndex - 0x64       (for base-game zones, fileTableIndex ≥ 0x64)
```

**Important:** changing the zone ID alone loads the new zone's geometry but keeps the
existing camera spline data, which was authored for the original zone's coordinate space.
The camera will likely be underground or outside the map.  To fix this, update the
corresponding `ct##` control track keyframes (XYZ positions) and `cg##` spline nodes
to positions valid within the new zone.

### Can more zones be added?

The file has **no explicit count field** for zone sections — no `uint32 = 22` was found
anywhere in the file.  The engine most likely reads sections sequentially and stops at a
structural boundary (the scene graph footer / zone reference nodes that begin at `0x011e40`).

Adding a 23rd zone section is theoretically possible but requires:

1. **Growing the file** — insert the new zone section bytes between the last existing section
   and `0x011e40`, shifting the zone reference nodes and adjusting the file size in the FTABLE.
2. **Adding camera data** — author new `cg##`/`ct##` spline nodes in the scene graph area
   (`0x002600`–`0x00de00`) for the new zone's camera paths.
3. **Adding weather blocks** — the new zone section needs its own weather/fog sequence.
4. **Risk: unknown engine limit** — the engine may have a hardcoded cap on zone section count.
   22 is the observed vanilla limit; whether 23+ is safe is untested.

Editing existing zones (patching a zone ID and updating camera splines) is lower risk than
extending the section count.

## Weather / atmosphere sequence

Each zone section contains a weather sequence — a list of named weather-state blocks
that define the atmospheric conditions and fog seen during that zone's title screen segment.

### Weather tags observed (in file order)

```
clod  mist  clod  snow  mist  snow  mist  clod  suny  fine  mist  clod  fine  suny
fine  suny  rain  suny  loop  suny  fine  dryw  loop  clod  suny  fine  suny  rain
clod  fine  suny  clod  fine  suny  clod  fine  clod  mist  fine  suny  fine  suny
mist  suny  thdr  mist  suny
```

| Tag | Meaning |
|---|---|
| `fine` | Clear / fair weather |
| `suny` | Sunny |
| `mist` | Misty / foggy |
| `clod` | Cloudy |
| `snow` | Snow |
| `rain` | Rain |
| `thdr` | Thunder |
| `dryw` | Dry wind |
| `aura` | Aura / special atmosphere |
| `loop` | Animation loop marker |

### Weather block structure (common layout)

All weather tags (`mist`, `clod`, `snow`, `suny`, `fine`, `thdr`, `rain`) share the same
32-byte record structure, followed by a variable-length sub-record list:

#### Main record (32 bytes)

```
+0   char[4]  tag          weather type ("mist", "clod", "suny", …)
+4   uint16   entry_type   0x037d = populated entry
+6   uint16   reserved     0x0000
+8   uint16   blend_in     transition-in duration (frames / engine ticks)
+10  uint16   blend_out    transition-out duration
+12  uint8    color_r      fog/atmosphere colour — red channel (0–255)
+13  uint8    color_g      green channel
+14  uint8    color_b      blue channel
+15  uint8    pad          0x00
+16  uint32   fog_flags    0x00000604 (constant across all weather types — fog equation config)
+20  uint16   fog_near     distance where fog starts (world units)
+22  uint16   fog_far      distance where fog reaches full density
+24  char[8]  ctrl_track   animation control track name, null-padded (e.g. "ct20", "cga1")
```

#### Sub-record list (variable length, follows main record)

After the 32-byte main record, a list of typed entries continues until a null terminator:

| Type value | Size | Meaning |
|---|---|---|
| `0x037d` | 28 bytes | Additional fog state (same layout as main record from `+4` onward, no tag prefix) |
| `0x0210` | 8 bytes | Secondary blend / transition config; carries a parameter (e.g. 30 frames) |
| `0x037c` | 8 bytes | **End-of-list terminator** (null entry) |

A block of 8 zero bytes between the main record and sub-records acts as an empty
placeholder entry.

## Scene graph footer (end of file, `0x011e40`–`0x012090`)

Three nodes appear at the end of the file with tags `0620`, `s101`, `1700`.  These are
**scene graph nodes** (camera sequence / binding descriptors), not zone references.  Each
has flags `0x062f / 0x1000` and a world scale constant of `396.0`.

These node labels (`0620`, `s101`, `1700`) also appear as `ctrl_track` references within
weather blocks earlier in the file — they are part of the camera animation system, not the
zone loading system.

The zone that renders for each node is determined by the zone section whose camera
splines are bound to that node, not by the node tag itself.

## Control tracks (`ct10`–`ct2b`)

27 named animation channels drive the camera and atmospheric animation:

ct10  ct11  ct12  ct13  ct14  ct15  ct16  ct17  ct18  ct19
ct1a  ct1b  ct1c  ct1d  ct20  ct21  ct22  ct23  ct24  ct25

Each control track is referenced by name in weather-block `ctrl_track` fields and

two distinct animated sequences (two zone slots or two scene phases).

## Investigation notes

### Corrections from initial analysis

- **"3 background zones"** — wrong.  There are 22 zone sections.  The earlier conclusion came
  from misreading the three scene graph footer nodes (`0620`, `s101`, `1700`) as zone
  references.  They are camera binding nodes.
- **Zone names (Beaucedine Glacier, Selbina, Ro'Maeve)** — wrong.  These were incorrectly
  inferred from the footer node tags.  The actual zones are identified in the zone section
  table above.
- **`0620`, `s101`, `1700` as zone identifiers** — wrong.  These are 4-byte scene graph node
  labels used by the camera animation system.  `s101` also appears as a `ctrl_track`
  reference name inside weather blocks.  The zone identity is stored as a `uint32` at the
  start of each zone section, not in any 4-byte ASCII tag.

### Unknown zones

Five sections reference ROM4 files whose zone names are not yet confirmed:

| # | Zone ID | DAT | Header |
|---|---------|-----|--------|
| 1 | 68 | `ROM4/0/21.DAT` | `d_ri` |
| 2 | 51 | `ROM4/1/99.DAT` | `wf_g` |
| 3 | 61 | `ROM4/0/14.DAT` | `f_ma` |
| 4 | 54 | `ROM4/0/7.DAT` | `d_pa` |
| 5 | 50 | `ROM4/0/3.DAT` | `t_gu` |

Sections 17–22 (ROM3) are also only partially identified.  To resolve names for all of
these, cross-reference against the zone name string table:

```
uv run xi ftable lookup <file_table_index>   # confirm DAT path
# then read zone name from ROM/165/84.DAT via ZoneNameTable (xim)
```

### Zone count extensibility

Tested by scanning for any `uint32 = 22` count field — none found.  The engine reads zone
sections as a stream and stops at the `0x011e40` footer boundary.  Adding a 23rd section
is theoretically possible (insert bytes before `0x011e40`, grow the file) but the engine
may have a hardcoded cap at 22 that would silently ignore extras or crash.  No test has
been done.  Patching existing zone IDs is safer and fully confirmed to work structurally.

### Camera keyframes were misread by one float

The `ct20` example above lists `453.27 9.06 15.19` and `366.72 7.16 10.13` as two
positions. The second is not a position: `366.72` is a separate field, and the keyframe
stride is 48 bytes, not 12::

    +0x00  float3  eye XYZ
    +0x0c  float   view distance
    +0x10  float3  look-at XYZ
    +0x20  float   t   (0.0 .. 1.0)

So `ct20` is a short dolly: eye `(453.27, 9.06, 15.19)` looking at `(446.69, 7.16,
10.13)`, moving to eye `(458.96, 0.19, 16.45)` looking at `(452.25, -0.87, 11.57)`.

The view-distance field **varies within a track** — `cga` tracks run 312 → 350 across
their keyframes. An early version of the exporter hoisted it to track level and flattened
that movement, which is why it is stored per keyframe.

### Which camera belongs to which zone

Listed above as unresolved. A zone's weather records name their control tracks, and those
names share a per-zone prefix:

| Zone | Tracks |
|---|---|
| 111 Beaucedine Glacier | `cga0 cga3 cga4 cga6 cgaa cgab` |
| 126 Qufim Island | `cqf0 cqf4 cqf6` |
| 106 North Gustaberg | `cgu5 cgua` |
| 141 Fort Ghelsba | `cgh0 cgh2 cgh7 cghc` |
| 24 Lufaise Meadows | `ct14 ct1a` |
| 25 Misareaux Coast | `ct20 ct23 ct25` |
| 4 Bibiki Bay | `cpaa cpad` |

Verified against geometry: `cgu5`'s four points all fall inside North Gustaberg's
placement extents (`x -740..824`, `z -420..1180`) at y 33–47, with the nearest scenery at
`(-337.5, 0, 422.5)` — a camera hovering above terrain looking at nearby rocks.

### Weather records come in two shapes

The 32-byte layout documented above is only one of them. Matching on `0x037d` alone finds
no weather at all for La Theine Plateau or Valkurm Dunes, because those use a shorter form
with no blend pair and no fog colour::

    long  (32B)  tag, 0x037d, blend in/out, rgb+pad, fog flags, near/far, track[8]
    short (28B)  tag, fog flags, near/far, track[8]

Both appear in the same file; the discriminator is the `u16` at +4 — `0x037d` for long,
`0x0604` (the fog flags themselves) for short.

### Time of day

There is no clock and no time field. What reads as time of day is the authored atmosphere
per segment: the fog colour tints the scene and the near/far pair sets visibility. A
record type the analysis above does not mention, `0x030f`, carries RGBA-looking values
(`(198,178,158,128)` warm, `(4,4,8,128)` dark blue) and is the likely ambient/light entry,
but that is inference from the byte patterns — it has not been changed and observed.

### Two node type constants, not one

Scene nodes carry `0x486` at +4 **or** `0x606`. Both hold the same keyframe layout, so
matching only `0x486` silently drops the second set — 15 of 54 camera tracks and 45 of
123 keyframes, including `cgu1` and `cgu8`. The `0x606` nodes are the richer paths: three
keyframes at t = 0, 0.667, 1.0, against the two an `0x486` node typically carries.

### Segment timeline

A zone section is a stream, not a table. Reading it in file order gives the sequence the
segment plays: each weather state names the camera track that flies while it is showing,
and `0x0210` entries between them carry frame counts.

```
section 12  zone 106 (North Gustaberg)
   1. suny  fog   900/900   rgb(0, 141, 39)    camera=cgu1   timing=[20]
   2. fine  fog     0/100   rgb(32, 29, 29)    camera=-      timing=[40, 60, 80]
   3. mist  fog  1000/1000  rgb(64, 206, 75)   camera=cgu8
   4. clod  fog   350/350   rgb(32, 137, 11)   camera=cgua   timing=[60, 50]
   5. fine  fog  1500/1500  rgb(64, 18, 23)    camera=cgu5
```

**Which segment plays first is not in this file.** Nothing resembling an order or an
index was found, and the 22 sections carry no sequence field. If the zone differs between
launches, the choice is made at runtime.
