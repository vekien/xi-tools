# ROM/0/24.DAT — Character Selection Control (`sel_`)

**Path:** `ROM/0/24.DAT`  
**Size:** 3,392 bytes (0x0D40)  
**Magic:** `sel_`  

This file is a small `sel_`-format control/scene file associated with the title/login or
character-selection flow. It does **not** look like a texture container, and it does **not**
match the `menu` element layout used by `ROM/0/1.DAT`.

Direct inspection shows a compact list of named records containing float-heavy transform-like
data plus a few control blocks named `main`, `mov1`, `mov2`, `loop`, and `end`.

Current best interpretation: this file is part of the title/login **scene sequencing and object
placement system**, not a 2D texture sheet and not a generic menu table.

## Common record shape

Many of the `s###` records follow a confirmed keyframe layout:

```
+0   char[4]   tag          e.g. "s100"
+4   uint32    type         usually 0x00000486, where the high byte tracks keyframe count + 2
+8   24 bytes  zeros        reserved / padding
+32  uint32    key_count    number of 0x30-byte keyframes
+36  uint32    flag         usually 0, sometimes 4
+40  ...       keyframes    key_count * 0x30 bytes
```

Each keyframe begins with position-like float triples:

```
+0x00  float32  x
+0x04  float32  y
+0x08  float32  z
+0x0C  float32  distance / scene parameter, often about 350.0
+0x10  float32  secondary x/rotation/look-at value
+0x14  float32  secondary y/rotation/look-at value
+0x18  float32  secondary z/rotation/look-at value
+0x1C  float32  usually 0.0
+0x20  float32  usually 0.0
+0x24  float32  usually 0.0
+0x28  float32  sometimes 1.0 on the final keyframe
+0x2C  float32  usually 0.0
```

This makes the first three floats of each keyframe the most plausible hex-edit targets for moving
the associated scene object or anchor. For example, `s100` starts at `0x00B0`; its keyframe positions
are at `0x00E0` and `0x0110`.

The float payloads strongly resemble 3D transform/state data rather than 2D menu coordinates.

Observed recurring float constants include:

| Value | Meaning |
|---|---|
| `0x43AF0020` (`350.001f` approx.) | repeated in many `s###` records; likely a shared scene parameter |
| `0x3F800000` (`1.0f`) | frequent record terminator / flag |

The exact semantic meaning of each `s###` node is still unknown, but the record/keyframe structure
is now stable enough for targeted experiments.

## `mov2`, `loop`, and `end`

`mov2` begins at `0x0C30` and appears smaller than `mov1`.

`loop` begins at `0x0CA0` and includes a reference back to `mov1`:

```
0x0D00  3B 04 00 00  00 00 00 00  "mov1"
```

`end` begins at `0x0D30` and likely terminates the block chain.

The sequence `main -> mov1/mov2 -> loop -> end` is consistent with a compact scene-state script.

## What this file is not

Direct evidence argues against the following interpretations:

- Not a texture DAT: there are no texture entry names, sizes, or TXD payloads.
- Not a `menu` DAT like `ROM/0/1.DAT`: there are no `menu    ` section headers or packed 2D
  element structs.
- Not a direct reference list for files in `FINAL FANTASY XI\mov`: no printable strings matching
  `.pmv`, `.bgw`, `mov999`, or `music999` were found.
